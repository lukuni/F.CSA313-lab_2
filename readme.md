## 4. Thresholds — SLO (Алхам 4)

**Сонгосон SLO ба үндэслэл:**

SLO-г Алхам 2-ын **5 VU baseline**-аас гаргав:

- Baseline p95 (5 VU, script.js, `results/run-05vu.txt`) = **241 ms**
- Анхны буфер ×1.2 хэрэглэж `p(95)<290` гэж тогтоогоод шалгахад **бодитоор FAIL гарсан** (доор тайлбарлав) — учир нь test.k6.io бол амьд, интернэтэд байрлах сервер тул тест ажиллуулах бүрдээ сүлжээний нөхцөл ялгаатай байдаг. Тестийн явцад ажиглагдсан хамгийн өндөр p95 нь 325.04 ms болсон.
- Иймд буферийг ажиглагдсан хамгийн их утга дээр үндэслэн дахин тооцоолов: 325.04 × 1.2 ≈ 390 ms → **`http_req_duration: p(95)<390`**
- `http_req_failed: rate<0.01` — 99% availability (POFOD<0.01) шаардлагад нийцүүлэв.

**Анхны оролдлого (буфер хангалтгүй байсан жишээ, `p(95)<290`):**


## 5. Дүгнэлт

1. Ачаалал (VU тоо) 5-аас 100 хүртэл өсөхөд throughput бараг шугаман байдлаар 7.49 req/s-ээс 146.35 req/s болж өссөн (~19.5x, VU харьцаа ~20x-тэй ойролцоо) — тестийн зорилтот сервер зэрэгцээ хүсэлтийг сайн даадаг болохыг харуулна.
2. p95 latency 5, 30, 100 VU-ийн аль алинд нь **бараг тогтвортой** (238–246 ms) хэвээр байсан нь тестэлсэн ачааллын хязгаарт (100 VU хүртэл) ноцтой саатал ажиглагдаагүйг харуулж байна.
3. Error rate бүх гурван түвшинд **0.00%** хэвээр байсан бөгөөд `dial: i/o timeout` төрлийн алдаа огт гараагүй — өөрөөр хэлбэл 100 VU хүртэл availability доройтоогүй.
4. Хамгийн чухал ажиглалт: **нэг ижил тохиргоо (5 VU)-оор өөр өөр удаа ажиллуулахад ч p95 231мс-ээс 325мс хооронд хэлбэлзсэн** — энэ хэлбэлзэл нь VU тооны нөлөөнөөс (5→100 VU-д ердөө 238-246мс хооронд хэлбэлзсэн) илүү их байв. Энэ нь амьд, интернэтэд байрлах endpoint дээр ажиллахад сүлжээний хэлбэлзэл нь ачааллын нөлөөнөөс илүү давамгайлж болохыг харуулж байна.
5. Иймээс анх сонгосон ×1.2 буфер (`p(95)<290`) бодит дахин ажиллуулалт дээр FAIL гарсан — SLO-гийн буферийг зөвхөн нэг baseline рангаас биш, олон удаагийн ажиглалтын хамгийн их утгаас гаргах нь илүү найдвартай гэдгийг практикт харуулсан.
6. Санаатайгаар хатуу `p(95)<10ms` SLO тавьж FAIL тест хийхэд систем 232.67ms-тэй гарч threshold зөрчигдсөнийг k6 зөв илрүүлж, exit code-оор алдаа мэдээлсэн — энэ нь CI/CD pipeline дэх quality gate-тэй яг адилхан ажиллагаа.
7. Error rate threshold (`rate<0.01`) бүх тестэд 0.00%-иар давж биелсэн — манай тохиргоонд (тестэлсэн хязгаарт) availability биш, харин **latency-гийн хэлбэлзэл** илүү анхаарал татах хэмжүүр байв.
8. Ерөнхийдөө лекцийн "load өсөхөд эхлээд latency, дараа нь availability доройтдог" гэсэн загвар манай өгөгдөлд тодорхой ажиглагдаагүй (100 VU хүртэл); харин амьд гадаад endpoint-той ажиллахад **run-to-run variance**-ийг SLO/threshold сонгоход заавал тооцох ёстойг энэ туршилт баталсан.

## 6. AI ашигласан туршилт (нэмэлт)

_Хиймэл оюун ухаан (AI) ашиглан k6 ачааллын тестийн скрипт үүсгүүлэхэд үйл явц харьцангуй хялбар байсан хэдий ч анхаарах зүйлс цөөнгүй байв. AI-аас гарч ирсэн анхны скрипт нь бүтцийн хувьд зөв байсан ч target URL-ийг `http://localhost:8000` гэж санал болгосон бөгөөд энэ нь даалгаврын жинхэнэ зорилт болох `https://test.k6.io`-той нийцэхгүй байв — үүнийг гараар илрүүлж засах шаардлагатай гарсан. Мөн AI-ийн санал болгосон SLO буфер (×1.2, нэг удаагийн baseline дээр үндэслэсэн) нь бодит амьд endpoint дээр ажиллуулахад хангалтгүй болж, threshold тест бодитоор FAIL гарсан. Үүнээс болж буферийг олон удаагийн ажиглалтын хамгийн их утга дээр үндэслэн дахин тооцоолох шаардлагатай болсон. Энэ туршилт нь AI-ийн санал болгосон тохиргоог шүүмжлэлгүйгээр хуулж ашиглах нь эрсдэлтэй бөгөөд, ялангуяа амьд/гадаад системтэй ажиллахдаа бодит хэмжилтээр баталгаажуулах шаардлагатайг тод харуулсан._
