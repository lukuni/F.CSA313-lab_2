`k6 run --vus N --duration 30s script.js | tee results/run-NNvu.txt` командаар тус тусад нь ажиллуулсан. Бүтэн текст гаралт: `results/run-05vu.txt`, `results/run-30vu.txt`, `results/run-100vu.txt`.

| VU тоо | p90 (ms) | p95 (ms) | Throughput (req/s) | Error rate |

## 4. Thresholds — SLO (Алхам 4)

**Сонгосон SLO ба үндэслэл:**
- `http_req_duration: p(95)<4.5` (мс) — 30 VU-гийн baseline p95 ≈ 3.76 ms дээр үндэслэн, үүнийг ×1.2 орчим нэмэгдүүлж 4.5 мс-ийг тогтоосон. Учир нь baseline нь өөрөө сүлжээний бага зэрэг хэлбэлзэлтэй тул шууд baseline утгыг SLO болгож болохгүй, харин бага зэргийн зай (buffer) үлдээх шаардлагатай.
- `http_req_failed: rate<0.01` — даалгаврын стандарт 99% availability (POFOD<0.01) шаардлагатай тохирсон.

**PASS гаралт** (`script-treshold-pass.js`, файл: `results/run-pass.txt`):
```
✓ 'p(95)<4.5' p(95)=4.01ms
✓ 'rate<0.01' rate=0.00%
```

**FAIL гаралт** (`script-treshold-fail.js`, санаатайгаар хатуу SLO `p(95)<1`, файл: `results/run-threshold-fail.txt`):
```
✗ 'p(95)<1' p(95)=4.75ms
✓ 'rate<0.01' rate=0.00%
ERRO thresholds on metrics 'http_req_duration' have been crossed
```

## 5. Дүгнэлт 

1. Ачаалал (VU тоо) 5-аас 100 хүртэл өсөхөд throughput бараг шугаман байдлаар 4.95 req/s-ээс 87.35 req/s болж өссөн — сервер VU-уудыг зэрэгцээ хариулах чадвартай болохыг харуулж байна.
2. Гэсэн хэдий ч p95 latency 5 VU-д хамгийн өндөр (36.71 ms) байсан нь VU тоотой шууд хамааралгүй, харин цөөн хүсэлттэй үед нэг л сааталтай хүсэлт p95-ийг мэдэгдэхүйц дээшлүүлдгийг харуулна — жижиг sample size дээр перцентиль хэмжүүр хэлбэлздэг гэдгийг батлав.
3. 30 болон 100 VU-д p95 3-4 мс орчим тогтвортой байсан нь дунд зэргийн ачаалал дор латенси тогтвортой хэвээр байгааг харуулсан.
4. Харин 100 VU-д error rate 0%-иас 1.14% болж өссөн нь лекцэд үзсэн "throughput өсөхөд latency биш, харин availability эхлээд эвдэрдэг" гэсэн зөрчлийн бодит жишээ болсон.
5. `dial: i/o timeout` алдаанууд нь сүлжээний/серверийн холболтын пул (connection pool) хязгаарт хүрснийг илэрхийлж байгаа бөгөөд энэ нь бодит үйлчилгээ дэх "saturation point"-ийн шинж юм.
6. Иймд манай тохиргоонд системийн "нэгж хэрэглэгчийн туршлага" 100 VU-д муудаж эхэлсэн гэж дүгнэж болно — 30 VU хүртэл найдвартай, 100 VU дээр аль хэдийн деградаци эхэлсэн.
7. SLO-гоо `p(95)<4.5ms` гэж тогтоосон нь 30 VU-гийн baseline дээр үндэслэсэн бөгөөд PASS тестэд `p95=4.01ms`-ээр амжилттай биелсэн.
8. Санаатайгаар хатуу `p(95)<1ms` SLO тавьж FAIL тест хийхэд систем 4.75ms-тэй гарч threshold зөрчигдсөнийг k6 зөв илрүүлж, exit code-оор алдаа мэдээлсэн — энэ нь CI/CD pipeline дэх quality gate-тэй яг адилхан ажиллагаа.
9. Error rate threshold (`rate<0.01`) хоёр тестэд хоёуланд нь 0.00%-иар давж биелсэн бөгөөд манай тохиргоонд latency илүү сул тал болохыг харуулж байна.
10. Ерөнхийдөө лекцийн "load өсөхөд эхлээд latency, дараа нь availability доройтдог" гэсэн загвар манай өгөгдөлд p95 биш харин 100 VU дээрх error rate дээр илэрсэн нь SLO сонгохдоо зөвхөн latency биш, availability-г ч заавал хамт хэмжих шаардлагатай гэдгийг баталсан.

## 6. AI ашигласан туршилт (нэмэлт, заавал биш)

_Хиймэл оюун ухаан (AI) ашиглан k6 ачааллын тестийн скрипт үүсгүүлэхэд үйл явц харьцангуй хялбар байсан хэдий ч анхаарах зүйлс цөөнгүй байв. AI-аас гарч ирсэн анхны скрипт нь үндсэн бүтцийн хувьд зөв байсан бөгөөд шаардлагатай модулиудаа оруулж өгсөн тул терминал дээр шууд амжилттай ажилласан юм. Гэсэн хэдий ч thresholds болон stages утгуудыг тухайн системийн бодит боломжид тохируулалгүйгээр ерөнхий хийсвэр байдлаар санал болгосон тул тэдгээрийг өөрийн локал серверийн хүчин чадалд тааруулан өөрчлөх шаардлага гарсан. Ялангуяа AI-ийн санал болгосон target URL болон туршилтын хаягийг шууд хуулж ашиглахаас өмнө шалгаж, шаардлагатай бол өөрийн локал сервер рүү чиглүүлэн засварлах нь чухал болох нь анзаарагдсан. AI нь скриптийг хурдан хугацаанд бүтээхэд маш тустай байсан ч тестийн зорилгод нийцүүлэн босго утга болон ачааллын түвшнийг нарийн тааруулах ажлыг өөрөө хийх шаардлагатайг энэхүү туршилт харуулсан._
